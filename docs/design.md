# Устройство примера

Идея вдохновлена статьёй Максима Никитина [«Оркестрация ИИ-агентов: когда нужно поправить в одном месте и не сломать всё остальное»](https://habr.com/ru/articles/1103656/), опубликованной 4 ноября 2026 года. Автор описывает управление работой через единого оркестратора, сохранение состояния вне сессий и проверку результата отдельным рецензентом. Важный для нашего опыта принцип — отделить сообщение исполнителя о готовности от приёмки.

В этом небольшом примере состояние, переходы и повторы задаёт BPMN. PostgreSQL хранит очередь, экземпляр и историю. LLM отвечает только за содержимое решения и ревью. Две роли имеют разные system prompt; рецензент получает исходную цель и последний черновик, исполнитель — цель, предыдущий черновик и замечания. После отрицательного вердикта шлюз проверяет лимит; после последней попытки процесс создаёт пользовательскую задачу для группы reviewers. Два прерывающих граничных таймера отслеживают общий срок итерации: таймаут также ведёт к человеку. Пока задача не выполнена, экземпляр остаётся running. Человек принимает или отклоняет результат и оставляет комментарий.

Это адаптация одного принципа статьи, а не реализация pepper-orchestrator. Здесь нет пакетов работ, нескольких репозиториев, инструментальных агентов и независимого выполнения тестов. Рецензент из другой модели уменьшает зависимость от самопроверки, но остаётся вероятностным проверяющим.

## Код

- `process/orchestrator.bpmn` — единственный исполняемый процесс и его диаграмма.
- `internal/bpmgen/` — сгенерированный граф; `model/` и `method_*.go` без заголовка Code generated — рукописные.
- `internal/orchestration/` — подготовка итерации и причины эскалации в обработчиках переходов; приложение получает граф через `orchestration.Processes(svc)`.
- `internal/ollama/` — реализация `engine.AIClient`, HTTP `/api/chat`, JSON Schema вердикта и дополнительная проверка ответа.
- `cmd/orchestrator/` — приложение: миграции, очередь, API, стандартная консоль go-bpm, метрики.
- `internal/scenarios/` — интеграционные сценарии нового процесса.

Собственный Go-модуль `github.com/nicolas-vp/go-bpm-ai-orchestrator`. Импорты движка и шаблонов генератора переведены на новый модуль. XML namespace `https://github.com/nicolas-vp/go-bpm/schema/1.0` сохранён для совместимости с моделлером.

Исходные примеры и тесты, которые исполняли только удалённые примеры, исключены. Общие вспомогательные типы тестов сохранены отдельно; независимые тесты движка, очереди, генератора и API остаются.

## Поведение при сбоях

Техническая ошибка не превращается в отрицательное ревью. Некорректный вердикт возвращается как ошибка обработчика: очередь повторяет вызов, после исчерпания попыток экземпляр имеет статус failed. Перезапуск приложения сохраняет ожидающие задачи в PostgreSQL; повтор упавшей задачи запускается явно через консоль.

Контекст модели берётся из её Modelfile. Поскольку контекст рецензента может быть меньше контекста исполнителя, большие задания и длинные ответы требуют настройки моделей: пример не измеряет токены и не разбивает входные данные на пакеты. Таймаут AI-попытки — 10 минут; бизнес-таймаут итерации по умолчанию 120 секунд и настраивается через aiTimeoutSeconds. Уже выполняющийся запрос к провайдеру не отменяется самим BPMN-таймером: движок отбрасывает поздний результат по сохранённому идентификатору ожидания. Две роли вызываются последовательно; внешние конкурентные запросы к тому же Ollama этим приложением не координируются.
